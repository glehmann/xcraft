# Design: reusing the builds that a rebuild reproduces

Status: proposed. With the build environment changes, 29 of the 43 packages of xcp-ng-dist rebuild identically
after a change of kernel-headers, 33 with the static archives made deterministic too, see [Experiment](#experiment).

## Problem

A package gets a new build ID when its build key changes, and its key covers the build IDs of the packages of ours it
is built against, see build-keys.md. So a change of one package renumbers all those built against it, directly or not,
even when their builds do not change: 42 of the 43 packages of xcp-ng-dist are built against kernel-headers. Each
new number is a new release, which the users download and install, for nothing, and which the CI builds again.

`xcraft reuse` avoids it by hand, for the changes known not to matter. This design does it automatically: a package
whose key changed is built, and when its build is the same as the one of its previous build ID, it keeps that build ID
and its build, and the packages built against it keep theirs, unless they changed otherwise.

## Why the builds differ today

The release suffix of a build, `%autorev`, has its build number, and the build environment puts the release in the
files, not only in the headers of the packages:

| What | Where the release goes | Why it is there |
|---|---|---|
| `%_unique_build_ids` | the build-id of every ELF file, which debugedit seeds with `%{VERSION}-%{RELEASE}` | a build-id identifies one build: the `.build-id` links do not conflict between versions installed side by side, like installonly kernels, and debuginfod or ABRT find one package by build-id |
| `%_unique_debug_names` | the names of the debug files, which `.gnu_debuglink` has in the binaries | the debuginfo packages of several versions or architectures installed side by side |
| `%_unique_debug_srcs` | the sources in the debuginfo, in `/usr/src/debug/<name>-<version>-<release>.<arch>` | the same, for debugsource |
| package notes, `%_package_note_flags` | a `.note.package` section in every ELF file, written by the linker | systemd-coredump names the package of a crashing binary, without the rpm database |
| dwz multifile mode | the name of the file of the debug information shared by the binaries of a package, `/usr/lib/debug/.dwz/<name>-<version>-<release>.<arch>`, which the debug files reference, so the CRC of the debug file in `.gnu_debuglink` of the binaries | the same as `%_unique_debug_names`: find-debuginfo always names it so, only `--dwz-single-file-mode` avoids it |

The files generated by a build have its time too, like the mtimes of the `.pyc` files, which they embed: rpm sets
`SOURCE_DATE_EPOCH` from the changelog, but does not clamp the mtimes to it, `%clamp_mtime_to_source_epoch` being
unset.

XCP-ng installs one kernel, and supports no live patching: nothing is installed side by side, so the macros and the
dwz multifile mode only help debugging several versions at once, and the package notes, the coredumps of binaries
without their package. Without the multifile mode, the debug information is not shared between the binaries of a
package: the debuginfo packages of those with several binaries are a bit larger.

## Build environment

xcraft builds with:

- `%_unique_build_ids`, `%_unique_debug_names`, `%_unique_debug_srcs` and `%_package_note_flags` undefined. A macros
  file cannot undefine them: they are tested with `%{?...}`, which defining them to `%{nil}` does not change. So
  `[macros]` of xcraft.toml gets `false` for a macro to undefine, which the builds pass to rpmbuild and dnf builddep as
  `--undefine`, and the parser of the specs to `rpm.delMacro()`;
- `%clamp_mtime_to_source_epoch 1`, in `[macros]`;
- `%_find_debuginfo_dwz_opts` with `--dwz-single-file-mode` added to the options of EL, in `[macros]`: not
  `%_find_debuginfo_opts`, which specs set, like the kernel's;
- the static archives of the build root made deterministic, like `ar D` does: the time, owner and mode of their
  members zeroed, by a step added to `%__os_install_post`. The `ar` of EL is not deterministic by default, and most
  build systems do not ask it to be, like OCaml's. The step edits the member headers itself: `objcopy -D` and
  `strip -D` fail on the archives of objects that are not ELF, like those of dev86.

The build keys cover `[macros]`: all the keys change once, which needs a full rebuild of all the packages.

rpm 4.20, after EL10's 4.19, builds in `%{_builddir}/%{NAME}-%{VERSION}-%{RELEASE}-build`: the release in the working
directory of the compiler, in the debug information, and in what ccache hashes with `-g`. When EL gets it, the builds
set `%_builddir` back, or ccache `hash_dir = false` with a base directory.

## Comparing two builds

Two builds are the same when they have the same packages, by name, each with:

- the same files: path, SHA-256 from the header (`FILEDIGESTS`), mode, owner, group, flags (config, doc...), link
  target, device, capabilities; not their mtimes;
- the same dependencies and capabilities (requires, provides, conflicts, obsoletes, the weak ones), with the release
  suffix of the build removed from those of the package itself, like `builds.recordable()` does, but not from those on
  other packages: a requirement on the new build of a dependency is a difference;
- the same scriptlets, triggers and their programs;
- the same source package, but its release: its spec and sources.

The rest is ignored: the release, build time and host, `SOURCERPM`, the signatures and digests of the headers and
payloads, which have them. The comparison reads the headers with python's rpm in the image of the host, as the result
does not depend on the architecture.

Ignoring too little only misses a reuse. Ignoring too much publishes a build that does not match its key: the ignored
fields stay few and explicit, and the debug packages are compared like the others.

## When to compare, and what is recorded

A package is compared when its new key has the source package of its previous build ID: the same package directory as
the build of that build ID, so that only its build root changed, from the build IDs of its dependencies or the lock.
Its previous build must be in the cache, or in the remote storage.

When the builds are the same, on all the architectures, the package keeps its previous build ID, which accepts the
new key, as `xcraft reuse` records it, and the new build is dropped. The packages built against it then have keys
with the same build IDs as before, so they are built again only when they changed otherwise.

To decide:

1. All the architectures must agree, as the build ID is the same on all: a change of a dependency may matter on
   aarch64 only. Either the decision waits for the builds of all of them, or one architecture decides, and the
   builds of the others check it, failing on a difference.
2. Like the records of the builds, the decision changes `xcraft.builds`: a local build makes it, to commit, and CI
   with `--locked` fails on it.

## Experiment

On a scratch clone of xcp-ng-dist, with the macros undefined, `%clamp_mtime_to_source_epoch` set in the specs of six
packages built against kernel-headers, and later the dwz single-file mode, they were built, then built again after a
change of kernel-headers, or of xen, with other build numbers, and the builds compared as
[above](#comparing-two-builds).

| Package | Kind | Same build number, new build root | Another build number |
|---|---|---|---|
| biosdevname | C, one binary | identical | identical |
| xcp-clipboardd | C, one binary | identical | identical |
| xcp-python-libs | Python, `.pyc` | identical | identical |
| xsconsole | Python, noarch | identical | identical |
| varstored | C, several binaries | `PK.auth` | binaries and debuginfo, by the dwz file; with the single-file mode, `PK.auth` |
| blktap | C, several binaries and libraries | the test results | binaries and debuginfo, by the dwz file; with the single-file mode, the test results |

With the build environment above, the binaries and their debug information did not depend on the build number,
and what still differed were files that the builds of two packages generate differently each time:

- `PK.auth` of varstored, made by `make PK.auth`: an authenticated EFI variable, with its time and signature;
- the `testresults` subpackage of blktap: logs of its tests in tarballs with their times, and the command of genhtml,
  with the build root path, which has the release.

### Full rebuild

All the 43 packages of xcp-ng-dist were then built on a scratch clone with the build environment above set in their
specs, but the deterministic archives, then built again after a change of kernel-headers: all the others got a new
build number, 42 of them being built against it.

29 packages were identical: biosdevname, branding-xcp-ng, dhcp, dmv-utils, edk2, guest-templates-json,
host-installer, ipxe, nbd, opam, openvswitch, python-bitarray, python-opentelemetry, qemu, ssmtp, vmss, vncterm,
xcp-clipboardd, xcp-emu-manager, xcp-featured, xcp-ng-config, xcp-ng-deps, xcp-ng-generic-lib, xcp-ng-release,
xcp-ng-xapi-plugins, xcp-python-libs, xo-lite, xsconsole and xs-opam-src.

The others, with kernel-headers itself, differed by:

| What | Packages | Fix |
|---|---|---|
| the member headers of static archives, their time and owner: the 371 differing archives had the same members | dev86, libempserver, ocaml, ocaml-findlib, only by them; xen, xapi, xs-opam-repo | deterministic archives, see [above](#build-environment) |
| the time of the build, in `include/generated/compile.h`, `utsversion.h`, `vmlinuz`; the headers tarball of `kheaders.ko`; perf, objtool, resolve_btfids | kernel | `KBUILD_BUILD_TIMESTAMP` from `SOURCE_DATE_EPOCH`, in the spec; the tools not studied |
| the release, `GRUB_RPM_VERSION`, in `config.h`, `version.mod` and the EFI binaries | grub | the spec |
| the release in the SBAT section of the EFI binaries, and their CodeView debug entry | xen | none for SBAT, made for the secure boot revocations, which has the release on purpose |
| the time of the build, in the build info of xenopsd-xc and xapi | xapi | the spec, from `SOURCE_DATE_EPOCH` |
| the times of the installed files, in the `.changes` files of opam | xs-opam-repo | the spec, or opam |
| the time of the ISO, in its volume descriptor | xcp-ng-pv-tools | the spec, with the dates of `xorriso` from `SOURCE_DATE_EPOCH` |
| `PK.auth` | varstored | the spec, see above |
| the test results, see above; the HTML coverage and test reports | blktap, sm | the spec, or the results out of the packages |

With the deterministic archives, dev86, libempserver, ocaml and ocaml-findlib are identical too: 33 of 43. Each of the
others keeps a new build ID on each change of its build root, like today, until its spec is fixed. The packages built
against them are still compared, and reused when identical: qemu, built against xen, was.
