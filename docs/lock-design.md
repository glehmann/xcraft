# Design: one lock, computed from one architecture

Status: proposal, for review.

## Build roots

The **build root** of a package is the set of packages installed in its build environment for its build: those of the
build environment image, plus those `dnf builddep` installs for its `BuildRequires`, with what they require in turn,
recursively. Some are ours, like `xen-devel` for a package built against xen, and the others upstream, like
`openssl-devel`. A package built against ours also gets what ours require, including what rpm generated for them when
building them, like `lzo` for `xen-dom0-libs`, which links against it.

What the lock calls the build root of a package is its upstream part, besides the image's: the image is the same for all
the packages, and its tag covers it in their keys, while our packages are in their keys through the keys of the packages
they are built against.

## The problem

Each architecture has its lock, `xcraft.<arch>.lock`, with the build roots of its packages: the upstream packages each
build installed besides the image's. They come from builds: a build records what dnf installed for its `BuildRequires`,
and the build keys use their locked versions. So a lock is complete only on an architecture where every package was
built at least once, and kept complete only by building there each change touching the build roots.

Most developers work on x86_64. The lock of aarch64 would lag behind, unless a bot built everything there and committed
its lock, which is not wanted. Today, `xcraft.aarch64.lock` has the packages of the image, and no build root at all.

What matters in a lock is the same on all the architectures: the versions of the upstream packages, which `xcraft lock
--update` already keeps the same. What differs is bookkeeping, which only builds on each architecture can do today.

## What the bitbake prototype did

`meta-almalinux`, generated by `dnf-bridge`, had one recipe per upstream source package: one version, all its binary
packages for x86_64_v2 and aarch64, with their checksums, and their dependencies, resolved by dnf from the metadata of
the repositories. The build roots were computed from these declarations, and enforced: each build only had a repository
with its declared closure. The requirements rpm generates when building our packages, like `liblzo2.so.2()(64bit)` for
`xen-dom0-libs`, were declared by hand in our recipes (`RDEPENDS:xen-dom0-libs = "lzo xen-libs"`), and checked after
the build (`do_checkinstall` installs each package with its declared dependencies only).

So it computed the build keys before any build, on any architecture. The cost was the declarations by hand.

## Proposal

Compute the build roots like bitbake, from the specs, but record the requirements rpm generates automatically, from the
builds, in the lock, which becomes one for all the architectures.

### One lock

`xcraft.lock` replaces `xcraft.<arch>.lock`:

```toml
# written by xcraft: the versions of the upstream packages, for all the architectures

[sources]                                   # by source package: all its binary packages take this version
"glibc" = "2.39-145.el10_2.alma.1"
"openssl" = "1:3.5.8-1.el10_2.alma.1"

[requires]                                  # generated by rpm, not in the specs: what our binary packages need
"qemu" = ["libaio", "libjpeg-turbo", "libpng", "pixman"]
"xen-dom0-libs" = ["e2fsprogs-libs", "lzo", "xen-libs"]

[requires.aarch64]                          # the rare differences of an architecture, replacing the entries
"xen-dom0-libs" = ["e2fsprogs-libs", "xen-libs"]

[provides]                                  # generated by rpm, not in the specs, and required by ours
"xen-devel" = ["pkgconfig(xenctrl) = 4.17.6"]

[buildrequires]                             # from %generate_buildrequires, not in the specs: what builds need
"xcp-python-libs" = ["python3-pip", "python3-setuptools", "python3-wheel"]

[pending."xen"]                             # by source package, as today otherwise
"openssl" = "1:3.5.2-1.el10_2"
```

- **`[sources]`**, one version by upstream source package, like `meta-almalinux`. On each architecture, the build
  environment locks the binary packages of that source in that version: those whose `sourcerpm` is the locked one, from
  the metadata of the repositories, the suffixes of `release_suffixes` apart. There is nothing left to align between the
  architectures, nor to check.
- **`[requires]`**, for each binary package of ours, the packages its generated requirements resolve to, by name, ours
  or upstream, but those its spec declares. Not the capabilities themselves: many have hashes, like `ocaml(Stdlib) =
  <hash>`, which change on most OCaml rebuilds, while the names are stable. The edges between our packages matter too:
  a generated requirement can bring another of ours into a build root, which brings its own. Builds record them, from
  the headers of the packages they made, before those built against them are built. A build made elsewhere, with a
  lock missing them, records them too when it is fetched from the remote storage, before it is used.
- **`[provides]`**, for each binary package of ours, the capabilities rpm generated for it that a spec of ours
  requires, as `BuildRequires` or `Requires`, with their versions. Only those: all of them would be thousands, and
  change on rebuilds, like `ocaml(Stdlib) = <hash>`. They go into the repository of our binary packages, so that
  `BuildRequires: pkgconfig(xenctrl)` resolves to `xen-devel`: an edge alone, in `[requires]`, would not make the
  synthetic `xen-devel` provide it. Builds record them from the packages they made, and keep all their provides with
  their result in the cache and the remote storage, for a spec requiring one of them later, without a new build.
- **`[buildrequires]`**, for each source package of ours with `%generate_buildrequires`, the packages its dynamic
  `BuildRequires` resolve to, by name. rpm only knows them by running the spec's script, in a build, like `xcraft build`
  does today with `rpmbuild -br`. Builds record them, from the source packages `rpmbuild -br` makes with them.
- **`[requires.<arch>]`, `[provides.<arch>]` and `[buildrequires.<arch>]`**, the entries of an architecture that differ
  from the shared ones. An entry there replaces the shared entry of the same package on that architecture, rather than
  adding to it, so that it can also have less, or nothing, with an empty list. A build records its findings in the
  shared table when it has no entry for the package yet, or has the same one, and in the table of its architecture
  otherwise; one finding the shared entry again removes the entry of its architecture. When the shared entry changes,
  from the build of another architecture, the architectures without an entry of theirs get it, and their next builds
  check it, like any finding. No package is named after an architecture, which these tables are named after.
- **No checksums of the binary packages:** the repositories sign them, and dnf checks it (`gpgkey` of the repositories).
- **No build roots:** they are computed.

### Build roots, computed

For each package, xcraft resolves its `BuildRequires`, and its `[buildrequires]`, with dnf, without installing
anything, against:

- the upstream repositories, at the locked versions;
- a repository of our binary packages, written from their parsed specs: names, versions, provides and requires, plus
  their `[requires]` and `[provides]`. Only its metadata is needed, not the packages.

When a spec requires a capability nothing provides, the resolution looks for it in the provides kept with the current
builds of ours, in the cache or the remote storage, and records it in `[provides]`. When no current build has it, like
a capability of a package of ours not built yet since a change, the resolution fails, saying so: building that package
first records it.

Resolving only reads the metadata of the repositories, so one machine resolves for all the architectures, natively:
`--forcearch`, as xcraft already does to prepare the dnf cache of an emulated architecture. The image is resolved the
same way, from `packages` of `xcraft.toml`, and its tag computed from the result.

### Specs, parsed for each architecture

The repository of our binary packages of an architecture comes from the specs parsed for it: `%ifarch`, `%{_arch}`,
`%{_libdir}` and the like change their binary packages, provides and requires. Today, xcraft parses them in the image of
the architecture, under emulation for the other ones.

They are parsed natively instead, in the image of the host, for each target, like `rpmbuild --target`:
`rpm.reloadConfig("<arch>-linux")` sets `%_target_cpu`, which `%ifarch` tests, and reads the macros of the platform,
`/usr/lib/rpm/platform/<arch>-linux/macros`, which the `rpm` package has for all the architectures, `x86_64_v2`
included.

What this misses are the macros of packages of the image of the target that differ from the host's: most macro packages
are `noarch`, but nothing guarantees it. So the builds check the parsing: see below. `xcraft doctor` can also compare,
once, the native parsing of the whole tree with the emulated one.

### Checked builds

A build records what only a build can know, then checks the computation, for what it installs and what it makes.

The discrepancies are of two kinds. Those of the requirements and provides rpm generates, which the specs do not have,
are expected: the build records them in the lock, without `--locked`, and fails with them with `--locked`, in CI. Those
of what the specs have, as parsed for the architecture, or of the resolution, are errors: nothing in the lock represents
them, the build fails, and they are fixed in the spec or in xcraft.

| Discrepancy | Found | Repair |
|---|---|---|
| A generated requirement, new or changed | in the headers of the packages it made, or of a fetched build | recorded in `[requires]`, or `[requires.<arch>]` when it differs on an architecture |
| A generated provide required by a spec of ours | in the headers of the packages it made | recorded in `[provides]`, or `[provides.<arch>]` |
| A dynamic `BuildRequires`, new or changed | in the source packages of `rpmbuild -br`, before installing them | recorded in `[buildrequires]`, or `[buildrequires.<arch>]` |
| Installed packages other than the build root, computed again with what it recorded | after installing the build dependencies | failure: an error of the resolution, like dnf choosing another provider, see *Determinism* |
| Packages made other than those parsed: a binary package, its version, its declared provides or requirements | after the build | failure: the parsing is wrong for the architecture, fixed in the spec or in xcraft |

What a build records can change its build root, so its key. Its result is cached under the key of the build root
computed again with what it recorded, when that is the build root it got. Otherwise, it is not cached: xcraft plans the
builds again, with the new edges, and builds it again, after the packages of ours it now needs, which may have to be
built first. A build can never be cached under a key that missed something it got.

The repository of our builds a build sees only has the builds of its dependencies, not all the current ones: an edge
missing between our packages fails at once, in `dnf builddep`. For the dynamic `BuildRequires`, the build writes the
requirements of each source package of `rpmbuild -br` before installing them, so that xcraft records them even when
`dnf builddep` fails on one of ours missing there, then plans again. The upstream repositories are not restricted: the
check covers them.

That makes the computation safe without declaring anything by hand: the builds check it.

### Keys

They do not change in their principle: the package directory, the image, the recipe, the keys of the packages it is
built against, and the versions of its build root, which is now computed instead of recorded. So every key, on every
architecture, is known before building there, once the lock has the `[requires]`, `[provides]` and `[buildrequires]`
of the builds.

The one exception is a change adding something only a build finds: a new generated requirement or provide, a new
dynamic `BuildRequires`. Its key is right after its build, which records it, and its commit, which CI checks with
`--locked`.

### The rest of the lock

- **`xcraft lock --update`** takes for each source package the latest version all the architectures have, as today,
  resolving their metadata natively. `--arch`, `--available` and `--check` go away.
- **`xcraft impacts`** works on the computed build roots, by source package, for all the architectures at once.
- **`runtime`** stays as it is: `xcraft publish` resolves it from the built packages, which it has.

## Workflows

- **An AlmaLinux update:** `xcraft lock --update`, on any machine. One decision for all the architectures; the impacted
  packages are known without building.
- **A new `BuildRequires`:** the resolution finds a package not locked, and adds it, at the latest version all the
  architectures have, with the change of the spec. From x86_64, for aarch64 too.
- **A package generating a new requirement,** like linking a new library: its build records the edge in `[requires]`,
  before the packages built against it, which are built after it. With `--locked`, CI refuses it until it is committed.
- **A new dynamic `BuildRequires`:** its build records it in `[buildrequires]`, and when it is one of ours, builds again
  after it.
- **A `BuildRequires` on a generated provide of ours,** like `pkgconfig(xenctrl)`: the resolution finds it with the
  current build of its package, or the next one, and records it in `[provides]`.
- **A requirement, provide or dynamic `BuildRequires` of one architecture only, or missing on one:** the build there
  records its own entry, in `[requires.aarch64]`, `[provides.aarch64]` or `[buildrequires.aarch64]`. It should be rare:
  the generated requirements are the same on x86_64 and aarch64, `()(64bit)` included.
- **A new architecture:** nothing to record. Its first builds check the lock, and the parsing of the specs for it.

## Measurements, on xcp-ng-dist

- 151 binary packages of ours have generated requirements, 3484 distinct ones; most are satisfied by our packages.
- 21 upstream packages outside the image come only from generated requirements of ours, like pixman, libpng and
  libjpeg-turbo, from qemu, lzo, from xen-dom0-libs, or pciutils-libs, from biosdevname and xapi-core. They are in the
  build roots of up to 16 packages, without their specs asking for them. A computation from the specs alone would miss
  them, hence `[requires]`.
- No `BuildRequires` of ours needs a package of ours only through a provide rpm generates, like `pkgconfig(xenctrl)`.
  When one does, `[provides]` records it.

## Migration

1. `[sources]` from `xcraft.x86_64_v2.lock`, by its `source` field, checking that aarch64's agree.
2. `[requires]` and `[provides]` from the latest builds of x86_64_v2, as for the measurements above, and
   `[buildrequires]` from their logs, or their next builds.
3. `xcraft.<arch>.lock` removed. All the keys change: one full rebuild, on each architecture.

## Risks and open questions

- **Determinism.** The resolution must give the same result everywhere. The locked versions fix the candidates, but
  dnf chooses between alternatives, like several packages providing the same capability. If that happens, the lock
  records the choice, like `DEFAULT_RPM_RPROVIDERS` of `dnf-bridge`.
- **`--forcearch` and the native parsing.** The resolution and the parsing for aarch64 from x86_64 only read metadata
  and macros, but they have to be checked against real aarch64 builds: the checked builds there do it, each time.
- **Unresolved requirements.** The measurements found 7 requirements of our opentelemetry packages with no provider,
  like `python3.12dist(requests)`. They have to be fixed first: the resolution fails on them.
- **Size of the change.** `lock.py`, the keys, `impacts`, the build environment, and the tests of all of them. It can
  land in steps: the lock format, the native parsing and the computation first, with the check of what builds install,
  which replaces today's `_check_build_root`; the check of what they make and the restricted repository of our builds
  next, with the recording of the dynamic `BuildRequires` before installing them.
